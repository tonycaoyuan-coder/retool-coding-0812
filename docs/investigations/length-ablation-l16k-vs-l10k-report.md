# ReTool-Coding 0812：L16K/24K vs. L10K/20K 长度消融深度分析

> 生成日期：2026-08-17
> 比较对象：Base、C0@40、C1@100、C2@100 × C0/C1/C2 test prompt，共 12 个 cell；每个 cell 为同一批 200 题。
> 差值方向：除非另有说明，均为 **L16K/24K − L10K/20K**；`pp` 表示百分点，不是百分比。
> 结论边界：这是同题配对的 post-hoc 重跑比较。由于两批轨迹没有保持逐 token 前缀一致，本文只作行为关联描述，不把结果翻转归因于“额外 token 本身”。

## 1. 执行摘要

1. **数据完整性审计通过，没有缺失 cell 或损坏轨迹。** 新实验 `2,400/2,400` completed；12 个 cell 均为 200 条；C0/C1/C2 使用完全相同的 200 个 sample ID。SQLite、prediction、score、trajectory 数量逐层一致。对新实验全部 15,468,406 个 completion token，逐 turn 的 `completion_token_count == len(completion_tokens) == len(logprobs)`，且 logprob 全为有限数；SQLite 汇总的 prompt/completion 计数逐条吻合。
2. **总体 pass@1 没有改善。** pass@1 为 `33.71%→33.63%`（`-0.08pp`；137 个正向 flip、139 个反向 flip）；按 sample ID 聚类的 case/public/private 平均变化分别为 `+1.04pp [-0.18,+2.34]`、`+1.03pp [-0.47,+2.53]`、`+0.96pp [-0.29,+2.25]`，均跨 0。不能声称增长预算提高了总体正确率。
3. **交付率略好，但成本显著增加。** format-valid 为 `70.50%→72.79%`（`+2.29pp`），cap-hit 为 `30.17%→27.96%`（`-2.21pp`）；同时平均 completion 增加 `+1,768 [+1,459,+2,084]` tokens，未提交 tokens 增加 `+1,652 [+1,356,+1,961]`，完整轨迹 latency 增加 `+26.2s [+21.7,+30.9]`。中位 completion 反而近乎不变（`2,621→2,618`），说明均值成本主要由长尾拉动。
4. **平均改善掩盖了显著异质性。** 最清晰的正向 cell 是 `C2@100 × C2`：format-valid `+7.0pp`、cap-hit `-7.0pp`，两者 exact McNemar `p=0.0066`，但 pass@1 仅 `+1.0pp`、`p=0.845`。`C2@100 × C1` 的 cap-hit 也下降 `7.0pp`（`p=0.020`）。相反，Base×C0 和 C0@40×C0/C2 的 cap-hit 上升，C1@100×C2 上升 `4.5pp`。没有“所有模型、所有 prompt 一致受益”的结论。
5. **所谓“挽救”与“只增加成本”同时存在，而且不是干净的 continuation 反事实。** 原实验 724 条 cap-hit 中，新重跑有 `232/724=32.0%` 形成合法提交、`40/724=5.5%` 正确、`506/724=69.9%` 仍触顶、`492/724=68.0%` 仍无 final。全体 2,400 对中，`1,228/2,400=51.2%` 使用更多 completion tokens 却没有 pass 或 format 改善，`645/2,400=26.9%` 使用更多 tokens 后仍是 invalid 且未通过。更关键的是，724 条基线 cap 中 **0 条**在新实验中保留完整旧首轮 token 前缀后继续生成；40 条“cap→pass”的首轮共同前缀中位数仅 141 tokens。因此这些数字是配对重跑转化率，不是额外预算的因果挽救率。

## 2. 实验、协议与可比性

### 2.1 固定项

逐项比较三个旧 `resolved_config.yaml`、三个新 `resolved_config.yaml`、manifest、SQLite `request_json/condition_json` 后，以下项目一致：

- 基座均为 `Qwen/Qwen3.5-4B`；权重 URI 完全一致：Base、C0 seed-42 step 40、C1 seed-42 step 100、C2 seed-42 step 100。
- experiment seed 与 generation seed 均为 42；逐题派生 seed、`temperature=0.0`、`top_p=1.0`、`top_k=-1`、`n=1`、`pass_k=[1]`、空 stop list 一致，即标称 greedy decoding。
- P1 工具协议保持：最多 1 次工具调用、最多 2 个 assistant turn、工具响应最多 512 tokens；tool timeout 5s。
- 冻结测试集一致：`formal-v6/test.jsonl.gz`，SHA-256 `014e784d…d630`，dataset fingerprint `ea61c69f…2af`；2,400 个新旧配对的 `sample_json`、sample ID、prompt 消息和 `prompt_hash` 逐条相同。
- C0/C1/C2 prompt 文本逐字一致；Docker image、case timeout 3s、judge timeout 30s、evaluator version `creator-v1+google-ifeval-e6890f8`、`creator-myeval 0.2.0`、`pytrio 0.2.5` 一致。

### 2.2 唯一预期研究差异与实际附带差异

设计上唯一预期的研究差异是两个长度上限；逐项核对实际配置时，另发现为容纳合法 16K 生成而同步放宽的 task watchdog。换言之，除下表三项及纯命名/落盘字段外，模型、数据、prompt、generation、P1 工具和 judge 协议参数一致；但实际处理不是只有两个 token 数发生变化。

| 参数 | L10K/20K | L16K/24K | 解释 |
|---|---:|---:|---|
| 单个 assistant turn 上限 | 10,240 | 16,384 | 核心长度处理，+60% |
| 完整轨迹 token 上限 | 20,480 | 24,576 | 核心长度处理，+20% |
| MyEval task watchdog | 300s | 600s | README 明确说明为容纳合法 16K 生成；它是处理 bundle 的一部分，不是纯长度不变量 |
| 实验名、输出路径、tracking job type、evaluation role 标签 | 旧实验标签 | 新实验标签 | 仅命名/落盘差异 |

`max_tool_calls`、`max_assistant_turns`、工具/判题限制等其余协议参数一致。旧批完整轨迹 latency 最大 `292.6s`，没有达到 300s；新批有 `34/2,400` 条超过 300s、最大 `413.0s`。因此 watchdog 增长在新批确实允许部分长轨迹完成；本文估计的是“更长 token 预算 + 相应 watchdog 放宽”的组合变化，不能进一步拆成纯 token-cap 效应。

另有两项 manifest/执行层限制：

- 新旧 manifest 的 `code_fingerprint` 分别为 `bf3f…05a9e` 与 `9502…6520`，benchmark plugin fingerprint 分别为 `f653…bd4d` 与 `a6d2…6181`；依赖版本和 evaluator version 相同，但仅凭现存产物不能证明执行代码与插件字节级一致。
- manifest 标记为 `seeded`，配置为 greedy，但重跑并非 token 路径可复现：2,400 对中只有 272 对首轮 token 序列完全相同；首轮共同前缀中位数为 158 tokens。这个事实是因果解释的首要限制。

### 3.2 统计口径

- 每个 cell 的分母固定为 200；总体描述性分母为 2,400。case/public/private 是先在每题内算通过率，再对题等权平均，不是把所有测试 case 合并。
- 二元指标对同一 cell 的同一 200 题做双向 flip 和双侧 exact McNemar。连续指标使用 10,000 次 paired bootstrap 95% CI；总体 CI 按 200 个 sample ID 聚类重采样，把每题的 12 个 model×prompt 观测作为一个 cluster。
- 12 个 cell 同时检验且未做多重比较校正；`p≈0.05` 只作为提示。总体 2,400 行包含同一题的 12 次重复，不能把朴素 pooled McNemar 当独立样本检验。
- 重复指标只在每个 assistant turn 内计算，不把 tool observation 纳入；“改口标记”匹配 wait/actually/rethink/different approach 等启发式短语。

### 7.4 为什么不能把转化写成“延长旧轨迹后成功”

若这是严格的 greedy continuation，旧轨迹在 10,240 tokens 触顶时，新轨迹至少应保留这 10,240-token 前缀再继续。实际检查显示：

- 2,400 对首轮完全相同仅 272 对；共同前缀中位数 158 tokens。
- 724 条旧 cap 中首轮完全相同仅 2 条，且两条都是旧批在第二轮而非第一轮触顶。
- 708 条旧 first-turn cap 中，没有一条旧首轮 token 列表是新首轮的完整前缀；“真实 continuation”计数为 0。
- 40 条旧 cap→新 pass 的共同首轮前缀中位数 141、最大 747 tokens；没有完整 10,240-token 前缀。

因此本报告把“延长预算挽救成功”改写为更谨慎的两类账本：**配对重跑的成功转化**（40/724）与**配对重跑的无可见收益成本**（1,228/2,400）。前者可能来自预算、batch/数值非确定性、代码/plugin 差异或其组合；后者也不能证明所有新增 token 都无用。

## 8. 工具使用

### 8.1 轮次口径

P1 总工具预算为 1。轨迹中工具 attempt 发生在第一 assistant turn：有效执行后插入 tool observation，才有第二 assistant turn。2,400/2,400 条都满足 `turns = 1 + valid_tool_calls`，且 `valid_tool_calls == tool_calls`；因此报告中的“第二轮”是 **post-tool final turn**，不是第二次工具调用。没有第二轮工具调用率可另行报告；协议与数据均为 0。

- `tool attempted`：第一轮文本中尝试发出工具调用，不要求语法/参数有效。
- `tool used`：至少一次有效调用实际执行；因为上限为 1，它也等于 mean tool calls 的非零率。
- `valid attempt rate`：`Σ valid_tool_calls / Σ tool_call_attempts`，分母是 attempts，不是 trajectories。

总体 attempted `98.08%→98.21%`（`2,354/2,400→2,357/2,400`），used `69.46%→71.58%`（`1,667/2,400→1,718/2,400`），valid-attempt `70.82%→72.89%`（`1,667/2,354→1,718/2,357`），mean calls `0.695→0.716`，mean turns `1.695→1.716`。变化很小，不能解释 +1,768 completion tokens 的主体。

## 13. 威胁与限制

1. **不是逐 token continuation。** 这是最严重的内部效度限制；所谓转化混合了长度、重跑非确定性和可能的实现变化。
2. **代码/plugin fingerprint 不同。** evaluator version、依赖、prompt、数据和配置参数一致，但不能从现存产物排除实现层差异。
3. **watchdog 同时变化。** 300→600s 是支持 16K 的合理操作调整，却意味着处理不是只改两个 token 数；34 条新轨迹超过旧 watchdog。
4. **单 seed、单次重跑。** bootstrap 只覆盖题目抽样，不覆盖训练 seed、推理 batch、服务负载或数值非确定性。
5. **多重比较。** 12 cells、多个指标产生大量检验；未校正 p 值应视为探索性证据。
6. **条件通过率有选择偏差。** valid/tool/no-tool 子集由模型行为产生；pass given X 只能描述关联。
7. **重复代理并非语义标注。** 重复行/8-gram 会把必要代码模式计入，也识别不了所有不重复的 dead-end chain。
8. **时延跨批受系统负载影响。** judge execution 可比性较好，完整 trajectory latency 还包含服务/batch 调度；它适合成本核算，不适合估算纯 token 速度。
9. **隐藏测试不可在轨迹级复核。** 这是预期的安全属性；本文只使用 judge 汇总计数，不展示隐藏内容。

## 14. 结论与建议

1. **不建议把 L16K/24K 作为全模型默认值。** 总体 pass 没有改善，平均 completion 和 latency 分别增加约 38% 与 40%；C0@40 甚至在模型平均上 cap 略升、pass 略降。
2. **若目标是减少未提交，优先针对 C2@100 做受控复验。** C2@100 跨 prompt 的 format `69.67%→75.50%`、cap `30.50%→24.33%`，但 pass 只 `38.00%→39.50%`；最强 cell 为 C2@100×C2。它值得复验，不足以直接上线。
3. **下一次实验必须做真正的 continuation 或提高可复现性。** 冻结 code/plugin fingerprint、固定 batching/并发，保存 10K 时的 KV/cache 或从同一 token prefix 继续到 16K；至少确认旧 10,240-token 前缀逐 token、逐 logprob 一致。否则“预算挽救率”无法识别。
4. **把 watchdog 设为独立对照。** 建议同时跑 L10K/20K+600s 与 L16K/24K+600s，或证明旧批没有 watchdog 截断；新批 34 条超过 300s，不能忽略这个组合处理。
5. **优先做终止控制而不是单纯加预算。** 在首轮和 post-tool 第二轮分别加入重复检测、剩余预算提示和强制提交阈值；同时报告 pass、format、cap、unsubmitted tokens、p95 latency。`3715` 表明第二轮也需要独立收束策略。
6. **保留双向账本。** 后续报告应同时给出 cap→valid/pass、pass/format 反向 flip、更多 token 无增益、仍 cap/仍无 final/仍高重复；避免只挑成功案例。
